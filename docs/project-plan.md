# 二手车数据采集与可视化平台 — 全栈项目计划书

> 求职作品项目 | 目标岗位：二手车公司·爬虫/数据采集技术岗
> 作者：邱子宏 | 技术栈：Python + FastAPI + MySQL + Next.js
> 合规声明：本项目仅采集公开可访问信息，遵守 robots.txt 与目标网站协议，控制请求频率，不绕过登录/付费墙，不采集个人隐私数据。

## 一、项目目标

### 1.1 业务目标

二手车公司的核心痛点是**定价与库存决策缺乏及时、结构化的数据支撑**。本项目围绕这一痛点，建设一个覆盖"采集 → 清洗 → 存储 → 展示"全链路的二手车行情数据平台：

1. **两条独立业务线并行采集**：新能源二手车（电车）与燃油二手车（油车），因车况评估逻辑、贬值曲线、核心参数差异巨大，拆分为两条独立的数据模型与采集策略；
2. **输出可直接使用的"干净表"**：按岗位要求，把"脏数据"整理成业务方可直接消费的 Excel / CSV / 数据库表；
3. **可视化看板**：为运营/产品提供价格行情、车龄分布、里程分布、保值率等实时视图，替代人工看车查价。

### 1.2 求职目标（对面试官展示的价值）

| 岗位要求 | 项目中的对应体现 |
|---|---|
| 对公开网站/平台信息进行数据采集 | 多站点采集器（瓜子二手车、懂车帝、汽车之家二手车等公开页面 + 公开行情接口） |
| 编写/维护爬虫脚本，定时/批量抓取，处理反爬与页面结构变化 | 调度系统（APScheduler）、UA池/限速/重试、选择器配置化（结构变化只改配置不改代码） |
| 清洗、去重、字段标准化，输出 Excel/CSV/数据库表 | pandas 清洗管道 + 去重指纹算法 + 多格式导出 |
| 搭建基础数据采集文档（字段说明、更新频率、异常记录） | 数据字典文档 + 采集日志表 + 异常告警 |
| 快速响应临时性数据提取与统计需求 | SQL 查询模板库 + 一键导出脚本 |
| Python（requests/BeautifulSoup/pandas） | 全部为核心依赖 |
| 加分项：Selenium/Playwright、正则、SQL、可视化、GitHub 作品 | Playwright 处理动态渲染页、正则清洗价格/里程、MySQL 存储、Next.js 可视化看板、全程开源 |

```
┌─────────────────────────────────────────────────────────────┐
│                        调度层（APScheduler）                   │
│        定时任务：每日增量抓取 / 每周全量校准 / 异常重试            │
└──────────────┬──────────────────────────────┬───────────────┘
               │                              │
   ┌───────────▼───────────┐      ┌───────────▼───────────┐
   │  采集层（两条业务线）     │      │   反爬与稳定性设施        │
   │  ├─ 新能源线 collector_ev│     │   ├─ UA 池 / 请求头工厂   │
   │  │   （懂车帝/电车资源等） │      │   ├─ 限速器（令牌桶）      │
   │  └─ 燃油线 collector_fuel│     │   ├─ 重试与降级           │
   │      （瓜子/汽车之家等）  │      │   └─ 页面快照（结构变化取证）│

   └───────────┬──────────────────────────────────────────────┘
               │
   ┌───────────▼───────────┐        ┌────────────────────────┐
   │   存储层（MySQL）        │        │   导出层                 │
   │   ev_vehicles /         │        │   Excel / CSV /         │
   │   fuel_vehicles /       │        │   临时取数 SQL 模板       │
   │   日志表 / 字段字典表      │        └────────────────────────┘
   └───────────┬───────────┘
               │ REST API（FastAPI）
   ┌───────────▼───────────┐
   │   展示层（Next.js）      │
   │   双业务线看板 / 对比分析  │
   └───────────────────────┘
```

**架构设计要点（面试讲述点）：**

1. **采集与清洗解耦**：原始响应先以 JSON 落盘（raw 层），清洗脚本可重跑，页面结构变化时无需重新抓取即可调试解析规则；
2. **两条业务线采集器独立、清洗管道共享框架**：新能源与燃油车分别独立采集器和数据表，但复用同一套清洗/去重/导出基建，体现"业务隔离 + 工程复用"的平衡；
3. **选择器配置化**：各站点的 CSS/XPath/JSON 路径写在 YAML 配置中，页面改版只改配置，体现"处理页面结构变化"的能力。

## 三、前后端职责划分

| 层 | 技术 | 职责 | 不做什么 |
|---|---|---|---|
| **采集端**（Python） | requests / BeautifulSoup / Playwright | 按业务线抓取公开页面与接口，原始数据落盘 | 不做业务计算 |
| **清洗端**（Python） | pandas / re | 字段标准化、去重、车型归一、写库 | 不关心数据从哪来 |
| **后端 API**（Python） | FastAPI + SQLAlchemy | 只读查询接口：列表/筛选/聚合统计/导出 | 不直接抓取 |
| **前端**（Next.js） | React + ECharts + Tailwind | 双业务线看板、车源列表筛选、油电对比分析、导出按钮 | 不做任何数据加工 |

> 说明：作为爬虫岗作品，采集与清洗层是绝对重心（约占 70% 工作量）；后端 API 与前端看板是"让数据被人直接用起来"的展示窗口，证明全栈交付能力。

## 四、两条业务线设计

### 4.1 为什么拆两条业务线（面试必讲）

| 维度 | 新能源二手车 | 燃油二手车 |
|---|---|---|
| 核心估值变量 | 电池健康度（SOH）、续航、是否首任车主质保 | 车龄、里程、发动机/变速箱工况 |
| 贬值曲线 | 前 3 年陡峭（技术迭代快）、受新车降价冲击大 | 平缓、受品牌保值率影响大 |
| 关键参数差异 | 电池类型、CLTC/NEDC 续航、充电功率 | 排量、变速箱类型、排放标准（国五/国六） |
| 数据源侧重 | 懂车帝新能源频道、各品牌官方认证二手车 | 瓜子/汽车之家等传统二手车平台 |
| 展示侧重 | 保值率曲线、电池衰减对比 | 价格分布、车龄-里程热力图 |

**结论**：数据模型、采集策略、展示模块全部独立，仅在工程基建层（去重、导出、日志）复用。

### 4.2 数据源与核心采集字段

#### 业务线 A：新能源二手车（ev_vehicles）

| 数据源 | 采集方式 | 频率 | 说明 |
|---|---|---|---|
| 懂车帝·二手车 | 接口抓包分析 + requests（JSON） | 每日增量 | 结构规整，字段最全 |
| 电动邦/电车资源行情页 | requests + BeautifulSoup（SSR 页面） | 每周全量 | 行业均价参考 |
| 品牌官方认证二手车页 | Playwright（动态渲染） | 每周 | 补充官方准新车价 |

**核心字段（数据字典节选）：**

| 字段 | 类型 | 标准化规则 | 示例 |
|---|---|---|---|
| vehicle_key | string | 去重指纹：MD5(平台+车源ID) | `dc_a8f3…` |
| brand / model | string | 归一化到标准车型库 | 比亚迪-汉EV |
| price_wan | decimal | 正则提取"X.XX万"，统一单位万元 | 15.98 |
| new_car_price_wan | decimal | 同上，用于算保值率 | 20.98 |
| mileage_km | int | "3.2万公里" → 32000 | 32000 |
| reg_year / reg_month | int | 上牌时间标准化 | 2022 / 06 |
| battery_type | enum | 磷酸铁锂 / 三元锂 / 未知 | 三元锂 |
| range_km | int | CLTC/NEDC 标注并保留口径 | 605 |
| battery_health | decimal | SOH 百分比（如有披露） | 91.5 |
| transfer_count | int | 过户次数，缺失记 -1 | 0 |
| source_platform | string | 来源平台标识 | dongchedi |
| captured_at | datetime | 抓取时间 | 2026-09-18 08:00 |

#### 业务线 B：燃油二手车（fuel_vehicles）

| 数据源 | 采集方式 | 频率 | 说明 |
|---|---|---|---|
| 瓜子二手车公开列表页 | requests + BeautifulSoup，翻页抓取 | 每日增量 | 车源量大，反爬中等 |
| 汽车之家二手车 | 接口抓包 + requests | 每日增量 | 字段规范 |
| 中国汽车流通协会公开月报 | 文档下载 + 表格解析 | 每月 | 宏观保值率基准数据 |

**核心字段（数据字典节选）：**

| 字段 | 类型 | 标准化规则 | 示例 |
|---|---|---|---|
| vehicle_key | string | 同上指纹规则 | `gz_1c9d…` |
| brand / model / series | string | 车型库归一 | 大众-朗逸 |
| price_wan / new_car_price_wan | decimal | 正则统一万元 | 6.80 / 12.49 |
| mileage_km | int | 标准化为公里 | 58000 |
| reg_date | date | 上牌时间 | 2021-03 |

- 字段说明、更新频率、异常处理规则统一沉淀在 `docs/data-dictionary.md`，直接对应岗位职责第 4 条。

## 五、数据存储方案

### 5.1 存储分层（三层数据湖式结构）

| 层 | 存储 | 内容 | 用途 |
|---|---|---|---|
| Raw 层 | 本地 JSON 文件（按日期分目录） | 页面/接口原始响应 | 溯源、解析规则调试 |
| ODS 层 | MySQL 原始表 `*_raw` | 清洗前数据，只追加不修改 | 保留脏数据证据链 |
| DWD 层 | MySQL 明细表 `ev_vehicles` / `fuel_vehicles` | 标准化后干净表 | API 查询、导出、看板 |

### 5.2 关键表设计

```sql
-- 业务线 A 明细表（节选）
CREATE TABLE ev_vehicles (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  vehicle_key VARCHAR(64) NOT NULL UNIQUE,      -- 去重指纹
  brand VARCHAR(50), model VARCHAR(100),
  price_wan DECIMAL(8,2), new_car_price_wan DECIMAL(8,2),
  mileage_km INT, reg_year SMALLINT, reg_month TINYINT,
  battery_type VARCHAR(20), range_km INT,
  battery_health DECIMAL(5,1), transfer_count TINYINT,
  source_platform VARCHAR(30), captured_at DATETIME,
  is_deleted TINYINT DEFAULT 0,
  INDEX idx_brand_price (brand, price_wan),
  INDEX idx_captured (captured_at)
);

-- 采集日志表（岗位职责第4条：异常记录）
CREATE TABLE crawl_log (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  business_line ENUM('ev','fuel'),
  source_platform VARCHAR(30),
  task_type ENUM('daily_incr','weekly_full','retry'),
  status ENUM('success','partial','failed'),
  fetched_count INT, dup_count INT, error_count INT,
  error_detail TEXT, started_at DATETIME, finished_at DATETIME
);
```

### 5.3 去重与更新策略

- **指纹去重**：`MD5(platform + 车源ID)` 唯一索引，重复数据走 UPDATE 更新价格而非插入；
- **同车多源**：预留 `match_key`（品牌+车型+年款+里程段+上牌时间）做跨平台同车匹配，为后续比价功能打基础；
- **下架追踪**：连续 3 次未抓到的车源标记 `is_deleted=1`，保留历史价格轨迹。

### 5.4 导出方案

- `export.py --line ev --format xlsx --date 2026-09-18`：一键导出当日干净表；
- pandas + openpyxl 输出带表头样式的 Excel；CSV 用于大批量场景；
- 内置 10+ 个常用 SQL 查询模板（如"某品牌近 30 天均价趋势"），应对运营临时取数需求（岗位职责第 5 条）。

## 六、反爬与合规设计（爬虫岗核心竞争力展示）

| 能力点 | 实现方案 |
|---|---|
| 限速 | 令牌桶算法，单站 QPS ≤ 1，随机间隔 3-8 秒 |
| UA 与请求头 | UA 池 + 每次请求随机化 Referer/Accept-Language |
| 动态渲染 | Playwright 仅用于接口抓包失败的页面，并复用浏览器上下文降低开销 |
| 重试与降级 | 指数退避重试 3 次，失败写 crawl_log 并告警 |
| 结构变化检测 | 解析结果字段缺失率 > 30% 时自动触发告警 + 页面快照留存 |
| 合规红线 | robots.txt 检查、仅公开页面、不破解验证码/登录、夜间低峰采集、遵守平台协议 |

> 面试话术锚点："我的原则是**robots.txt 一票否决、能拿接口不解析页面、拿不到接口才上 Playwright**——爬虫工程师的价值不是突破封锁，而是稳定、合规、低成本地拿到干净数据。"

## 九、项目亮点总结（面试官视角）

1. **业务理解力**：不是"爬个网站交差"，而是按二手车行业真实逻辑拆分油/电两条业务线，各有独立估值逻辑与数据模型；
2. **工程完整度**：采集 → 清洗 → 存储 → API → 可视化全链路闭环，三层数据结构可溯源；
3. **抗变化能力**：选择器配置化 + 字段缺失率监控 + 快照取证，正面回应"页面结构变化"这一爬虫岗日常痛点；
4. **合规自觉**：robots.txt 检查、限速、只采公开数据，主动写进架构设计；
5. **面向使用者的交付意识**：数据字典、异常日志、一键导出、SQL 模板库——把"脏数据"变成"别人能直接用的表"，与岗位职责逐条对齐。
