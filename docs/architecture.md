# 架构与设计决策

## 1. 分层与职责边界

```
调度 scheduler  →  源 registry  →  取数 fetcher  →  解析 parsers  →  加工 pipeline  →  存储 storage  →  导出 exporter
```

| 层 | 模块 | 职责 | 明确不做 |
|---|---|---|---|
| 调度 | `scheduler.py` | 按 cron 触发任务，单进程串行、单实例互斥 | 不关心抓什么、怎么抓 |
| 源 | `sources/registry.py` | 把 YAML 变成强类型配置，启动即校验 | 不发请求 |
| 取数 | `fetcher.py` | 合规闸门 + 限速 + 重试 + 三档降级 + 快照留证 | 不解析业务字段 |
| 解析 | `parsers/` | 从 DOM 取原始文案，监控字段缺失率 | 不做数值语义转换 |
| 加工 | `pipeline/` | 脏数据标准化、派生列、导出 | 不碰网络、不碰 SQL |
| 存储 | `storage/` | 校验 + UPSERT + 下架追踪 + 查询统计 | 不做业务清洗 |
| 编排 | `runner.py` | 串起全流程、隔离单源失败、写 crawl_log、告警 | 不实现具体抓取细节 |

**为什么拆这么细**：爬虫项目最常见的腐化是"一个 800 行的 `spider.py` 里抓取、解析、清洗、入库全混在一起"，
一旦目标站改版或字段口径调整，没人敢动。分层后，"选错了" 和 "抓错了" 和 "算错了" 是三类可独立定位的问题。

## 2. 关键设计决策（ADR 摘要）

### ADR-1 采集与解析解耦，原始响应落盘
**决策**：每次请求的响应以 `gzip + meta.json` 落盘（`data/raw/<line>/<date>/<source>/<hash>.html.gz`），
解析层只消费 HTML 字符串，不直接拿网络响应。
**收益**：解析规则改错时，用同一批快照重跑即可，不必重新抓取（既省时间，也减少对目标站的打扰）；
线上出问题时可回放取证。

### ADR-2 两条业务线独立建表，共享基建
**决策**：`ev_vehicles` 与 `fuel_vehicles` 字段完全独立，但共用限速、重试、去重、导出、日志组件。
**原因**：新能源车的残值由电池健康度、续航口径、电池类型决定；燃油车由车龄、里程、排量、排放标准决定。
强行合成一张表会得到一堆互斥的空字段，且统计口径互相污染。而基建是纯技术能力，复用能省一半代码。

### ADR-3 三档取数阶梯，默认从最省资源的档位起步
**决策**：`http`（Scrapling `Fetcher`）→ `stealth`（`StealthyFetcher`）→ `dynamic`（`DynamicFetcher`）。
响应被拦截或疑似 JS 空壳页时自动升档。
**原因**：HTTP 档位内存约 40MB、毫秒级；浏览器档位约 800MB、秒级。**能不开浏览器就不开**，
这是成本纪律，也是对大流量目标站点的基本礼貌。

### ADR-4 被拦截时升档而非原地重试
**决策**：`BlockedError.retryable = False`，403/429 直接进入下一档；只有网络抖动（超时、5xx）才原地重试。
**原因**：同一出口被风控拦下，原样重试 3 次只会加重风控标记；换更强的档位才有意义。

### ADR-5 状态码闸门
**决策**：在取数层强制校验 HTTP 状态码（`ensure_status_ok`）。
**原因（实测踩坑）**：Scrapling 的 `Fetcher` 对 404 **不抛异常**，会正常返回 Response。
若不做闸门，404 页面会被当作"成功抓取"的内容送去解析，最终污染数据。属于必须堵的死角。

### ADR-6 去重指纹 + 生命周期标记
**决策**：`vehicle_key = MD5(平台 + 车源ID)` 唯一键 UPSERT；`match_key` 做跨源同车归并；
`last_seen_at` + `missing_count` 判定下架（连续 N 轮未见 → `is_deleted=1`）。
**原因**：价格变动就是要追踪的业务信号，必须是 UPDATE 而不是 INSERT；
下架判定若用 `NOT IN (上千个ID)` 会拖垮数据库，用时间戳更稳。

### ADR-7 合规前置：配置档案 + 运行时闸门
**决策**：`config/sites.yaml` 固化 robots 核查结论（`robots_status` / `checked_at` / `note` / `allow_query_params`），
启动时硬校验，运行时 `RobotsGate` 再次联网复核。
**原因**：实测发现 **懂车帝、汽车之家二手车 robots.txt 均为 `Disallow: /`（全站禁止）**，
瓜子二手车 `Allow: /` 但 `Disallow: /*?*`（禁止带查询参数的 URL）。
这些结论必须落到配置里才能被审计，也必须被代码强制执行——否则"合规"只是文档里的一句话。

## 3. Scrapling 集成：实测结论与踩坑记录

> 版本：scrapling 0.4.15 / Python 3.13.14。

### 3.1 已验证可用

| 能力 | 验证方式 | 结论 |
|---|---|---|
| HTTP 取数 | 本地 HTTP 服务真实请求 | ✅ `status=200`，4 张卡片解析正确 |
| CSS / `::text` / `::attr()` 选择器 | 单元 + 集成测试 | ✅ 与 parsel 风格一致，可直接用 |
| `Selector(html, url=...)` 离线解析 | 夹具测试（零网络） | ✅ 适合 CI 与快照回放 |
| `auto_save=True` 指纹保存 | 实测保存 4 个元素指纹 | ✅ 保存动作正常 |
| 文档缺失率监控 + 快照 | 本项目实现 | ✅ 已被单元测试覆盖 |

### 3.2 实测**未达预期**，因此不作为依赖

| 能力 | 实测结果 | 本项目的处理 |
|---|---|---|
| `adaptive=True` 自动重定位 | 把 `class="car-item"` 改为 `car-card-v2` 后，普通选择器 0 命中、`adaptive=True` 同样 0 命中；显式配置 `SQLiteStorageSystem` 后仍为 0 | **不把"改版自愈"当作可用能力**。抗改版的主防线改为：选择器配置化 + 字段缺失率告警 + 快照回放；`adaptive` 参数按官方 API 接好，保留为待验证的可选项，需要按目标站点单独实测后再启用 |

**这条踩坑记录比"用上了某个高级特性"更有价值**：库的能力是假设，实测结论才是设计依据。
面试中能讲清"我验证过、它没达到预期、所以我改用可验证的降级方案"，比罗列特性清单更能说明工程判断力。

### 3.3 版本差异处理

- `Fetcher` 只有 `.get()`；`StealthyFetcher` / `DynamicFetcher` 只有 `.fetch()` —— 取数层按档位分派入口方法；
- 元素 `element.text` **只返回节点自身文本**，`<span class="price"><em>15.98</em>万</span>` 会只拿到 `"万"`；
  含子节点时必须用 `get_all_text()` —— 已封装为 `_node_text()` 并写入注释与测试；
- `adaptive` 与旧版 `auto_match` 参数名不同 —— 选择器封装做了一次兼容降级，降级时留 debug 日志，不静默吞异常。

## 4. 数据流与失败处理

```
请求前  → RobotsGate（robots.txt 一票否决，按 host 缓存）
        → TokenBucket（单站 QPS ≤ 配置值，默认 0.5）
请求中  → tenacity 指数退避重试（仅对 retryable 异常）
        → 状态码闸门（404/410 立即失败；4xx/5xx 按拦截或错误处理）
请求后  → 拦截/空壳检测 → 升档 or 返回
        → 快照落盘（gzip + 元数据，含内容 MD5）
解析后  → 必需字段缺失率 > 30% → SchemaDriftError + 告警 + 快照
        → 单条数据校验失败 → 丢弃并留样（不中断整批）
入库后  → 更新 missing_count；连续 N 轮未见 → is_deleted=1
```

**失败隔离**：单源失败不影响其他源；单条数据非法不影响整批；通知失败不影响采集。
**绝不静默**：所有丢弃、降级、跳过都会写日志（带 `trace_id`）并计入 `crawl_log.error_count`。

## 5. 可观测性

| 维度 | 载体 | 用途 |
|---|---|---|
| 任务级 | `crawl_log` 表 | 状态、页数、抓取量、入库量、去重量、拒绝量、缺失率、耗时 |
| 请求级 | 结构化日志（含 `trace_id`、tier、status、bytes、elapsed） | 定位"哪一页、哪一档、为什么失败" |
| 数据级 | `raw_ref` 指向的原始快照 | 回放、取证、规则调试 |
| 变化感知 | `schema_drift` / `source_failed` / `compliance_blocked` 告警 | 从"业务方发现没数据"提前到"系统主动发现" |

## 6. 已知限制

1. 单进程串行采集，源数量增长后需要换成 `scrapling.spiders.Spider` 并发框架；
2. 未接入代理池与分布式调度（多机部署时需要 Redis 做任务互斥）；
3. 无历史价格拉链表——目前只保留最新价格，无法直接算"降价幅度"，属于下一优先级；
4. 车型库目前是常量表（`cleaners.BRAND_ALIASES`），生产环境应改为数据表驱动并支持运营维护；
5. 真实站点的选择器需要现场用 `probe` 校准，仓库内的选择器是基于常见页面结构的初始值。
